# Budgefi product and system map

This document is the canonical map of what Budgefi currently does, which data is authoritative, and where the product intentionally stops. UI copy must not claim more than the implementation described here.

## Product contract

Budgefi is a household financial-operations workspace. It combines a conservative cash plan with source health, evidence-backed exception review, manual fallback, and a durable record of what changed. It never counts credit availability as cash, never counts expected income before it arrives, never moves money, and never claims to contact or cancel a merchant.

The current acquisition wedge is financial integrity: show whether source data is current, detect supported discrepancies, preserve evidence, collect a decision, and keep the outcome visible. The implemented detector is intentionally narrow: exact duplicate posted debits on the same account, within two days, after excluding pending replacements, transfers, savings round-ups, credits, samples, and known investment labels.

## Canonical data flow

1. Clerk proves a user identity; the API provisions or resolves a private household.
2. Every request runs through a restricted database login, assumes `budgefi_app`, and establishes user and household context inside one transaction.
3. PostgreSQL row-level security is the second authorization boundary. Canonical ledger tables force RLS. A small allowlist of operational queue/cache tables keeps RLS enabled but permits their owner-controlled `SECURITY DEFINER` functions to discover global work.
4. Money is stored and calculated as integer USD minor units. The server owns projections and calculation snapshots; the client only previews drafts. Independent canonical income schedules compete conservatively: the earliest active confirmed date sets the horizon, while any missed confirmed date forces the configured fallback until reviewed. Expected amounts are matching hints and never cash.
5. Every accepted mutation is idempotent, version checked where a user can overwrite state, audited, and increments the household data revision.
6. The client ignores older revisions, serializes mutations, and reloads canonical state after a rejected write.

## Source ingestion

Manual data and Plaid data enter the same accounts, balance observations and financial transaction ledger with explicit provenance. Plaid Link exchanges its public token on the server, encrypts the access token with versioned AES-256-GCM keys, stores the connection, and enqueues initial synchronization. The browser request does not wait for account/transaction history.

Changing provider evidence is grouped behind a stable logical transaction identity. Pending-to-posted replacements and later provider revisions therefore remain one feed item. Ingestion updates a deterministic current-evidence pointer on that identity; an indexed `(household, occurred date, identity)` path powers feed pagination without re-ranking the entire revision ledger. Categories are separate versioned decisions with explicit precedence: user choice, opt-in merchant rule, provider mapping, deterministic fallback. Provider taxonomy changes append evidence and never overwrite a user decision. Opt-in merchant rules are visible, version checked, editable, and retireable. The complete online feed is server-filtered and uses opaque keyset pagination; the encrypted identity-scoped bootstrap cache contains only a bounded recent preview.

Manual transaction corrections append a new evidence revision under the same logical identity; removal appends a terminal `removed` revision. Neither operation erases history, and an actual transaction cannot be created or corrected into a future household date. If a corrected or removed entry had been linked as plan evidence, that match is reopened rather than silently applying changed evidence. Plan items expose every active matched transaction and deep-link to its exact feed detail. Feed requests ignore stale responses during rapid filter changes, reconcile a refreshed bootstrap while mounted, deduplicate page boundaries, and bound the rendered mobile list while retaining an explicit route back to the newest page.

Migration 028 backfills transaction identities, current-evidence pointers, and conservative categories inside the migration transaction, so a failure rolls back cleanly and the migration runner can retry without a partially upgraded schema. The integration gate exercises a 10,001-entry pre-upgrade ledger and verifies that the bounded first-page query uses the current-state index without a window aggregation. Larger production ledgers require a measured maintenance window before rollout; the current early-access corpus is below that threshold.

Webhooks are signature and body-hash verified, deduplicated, and passed to a narrow database function that never reveals tenant identity to the request server. The function converts verified events into coalesced durable jobs or fixed connection-state changes. A dedicated scheduled Cloud Run job leases Plaid work, paginates from the committed cursor, reconciles accounts and transaction revisions, refreshes exceptions, persists a calculation snapshot, and updates connection health. Lease recovery, retry backoff and dead-letter state make host loss recoverable.

Disconnect immediately excludes connected accounts from new plans, detaches affected savings destinations, pauses their active contributions, clears affected income destinations and requires their dates to be reconfirmed, pauses automatic debt verification, and enqueues provider revocation. Verified goal, income, and debt history remains visible. A Budgefi-managed debt-payment commitment is deactivated and unlinked so a disconnected liability cannot keep reserving cash; an independently created commitment remains planned and visibly linked while bank verification is paused. The token is erased only after Plaid confirms removal or reports it already removed.

## Background operations

- `budgefi-plaid-sync`: restricted application database role; schedules and processes Plaid sync/revocation jobs.
- `budgefi-maintenance`: distinct worker database role; materializes dated recurring occurrences as the horizon rolls, marks overdue occurrences, prunes expired AI analyses, creates notifications, delivers APNs/email jobs, and finalizes confirmed account deletions.
- Schedule maintenance appends occurrence revisions and advances the household data revision. Calculation snapshots are request/ingestion checkpoints rather than an exhaustive daily time series; live bootstrap always recalculates from current occurrence evidence.
- Calendar schedules use one anchored recurrence kernel in the API and database. Quarterly means three calendar months and yearly means twelve; end-of-month intent survives short months and leap years. Every occurrence pins the exact commitment, savings, or income revision that created it. Rule edits skip unresolved superseded expectations but never rewrite verified history.
- Setup commitment slots have stable database identities independent of their user-facing names, so renaming “Rent” to “Mortgage” cannot recreate a second housing input after reload. Bootstrap returns recent user-explicit skips with their intent marker; system-superseded skips stay internal and never suppress a current preview or masquerade as a user decision.
- Reminders are generated from canonical occurrences, not directly from mutable rules. User preferences are versioned and pin channel, lead days, local time, quiet hours, and timezone into each immutable event. Delivery is separately leased with compare-and-swap completion, stale work expires after 24 hours, and paid, verified, skipped, or changed occurrences are suppressed before send. Maintenance leases one household at a time so one busy or broken household cannot block the full sweep.
- API instances do not own polling loops in production. Cloud Scheduler invokes both finite jobs, so scale-to-zero cannot suspend durable work.
- `deploy/gcp-plaid-worker.sh` is the checked-in deployment contract for the finite Plaid job and its scheduler. It references Secret Manager values and an immutable backend image; it does not contain credentials.

## Security and privacy invariants

- Provider and Clerk secrets never enter frontend bundles.
- Plaid and push tokens are encrypted at rest and redacted from logs/exports. Account exports include user-safe notification event and delivery history for auditability, but exclude encrypted tokens, destination hashes, and worker lease credentials. Export format 5 also includes common-bill starter lineage and available-cash alert evidence.
- New connected accounts are excluded from planning until the user includes them.
- Append-only activity, revisions, calculation evidence and case evidence reject ordinary update/delete.
- Onboarding drafts expire after seven days and are bound to authentication subject, household and server revision.
- Account deletion transfers household ownership before revoking a departing owner and finalizes only after provider access is revoked.
- Native cached financial state is encrypted/size-bounded, identity scoped and read-only while offline.

## Deliberate limits and open product work

The following are not currently complete and must not be marketed as complete:

- Merchant cancellation, negotiation, charge dispute or verified savings execution.
- General anomaly detection beyond the supported duplicate-debit rule.
- Household invitations, reimbursements, permissions UI and a multiple-household selector.
- Transaction-to-occurrence matching is deliberately conservative: only unique, high-confidence posted Plaid evidence from active cash accounts is automatic. Plausible but ambiguous evidence becomes a visible proposal on every candidate occurrence; choosing one rejects the alternatives without erasing their audit trail. Any posted transaction can be explicitly matched from Activity, inspected as proof on Plan, detached with the item-specific correction action, and reassigned. Confirmed evidence remains pending until a later same-account balance observation proves it is reflected; skipping a single occurrence is a separate action and never substitutes for correcting a match.
- Income sources are normalized versioned records, not fields on the plan. Each has its own optional matching amount, cadence, next date, optional destination, active/paused state, review reason, and immutable revisions. Weekly, biweekly, monthly, quarterly, yearly, and explicitly anchored twice-monthly schedules advance independently only after posted deposit evidence and later same-account balances verify the full occurrence; split deposits accumulate without advancing early. Irregular income never shortens the horizon or invents a next date. A user edit clears automatic lineage so historical deposits cannot overwrite it on a later sync. Household-scoped references and immutable revisions preserve advancement and reversal lineage. A transaction can support only one occurrence; ambiguous income candidates are presented for explicit selection. Onboarding shows multiple strong recurring-credit suggestions for explicit approval and keeps transfers, refunds, investments, and uncertain credits out. Detected commitment cadence is preserved through onboarding; unsupported twice-monthly commitments stay in explicit review rather than being coerced to monthly. Plan, Today, Activity, Connections, Settings, and Manual all read the same records and surface missed or disconnected sources as review work. Schedule maintenance shares the interactive planning lock, preventing stale-horizon materialization races. All alert types honor the user’s timezone and quiet hours, including connection, exception, and digest alerts. Export format 5 omits obsolete singular plan-income fields, makes `incomeSchedules` canonical, and includes preference revisions plus safe notification audit history; schedules and revisions also participate in deletion, row-level security, and calculation-snapshot manifests.

- “Add common bills” is a server-validated, commitments-only accelerator—not demo data. Nothing is preselected and selected rows begin with no amount or date, so they cannot change Available to use. Stable starter keys prevent duplicates after renaming, applications are atomic and idempotent, and an untouched batch can be undone as one operation. The default-off low-available-cash alert uses the exact persisted server projection shown on Today. It is serialized per user, rechecks freshness before event creation and final delivery, observes quiet hours, suppresses changed/recovered episodes, and rearms only after hysteresis.
- Planning periods and pay cycles are deliberately separate. Every calculated expected-income or fallback horizon appends a planning-period record, but a pay cycle begins only when a confirmed recurring-income occurrence is backed by a posted transaction and a later same-account balance observation. Same-day verified deposits coalesce into one boundary; irregular or merely categorized credits never invent a boundary. Once a cycle exists, `Earned` is the actual amount of every canonical posted credit categorized as income in an eligible deposit account inside it, including irregular and variable pay; verified schedule matches label sources but never gate or cap deposits. Protected income is reported but deliberately omitted from the spendable-cash reconciliation equation. An excluded account contributes income only when a verified schedule match explicitly makes it a cycle boundary; other protected/excluded spending stays outside the report, while verified savings movements remain a separate overlay. Reports use half-open local-date windows, actual receipt dates, point-in-time account-role and account-type intervals, verified savings/debt evidence, and immutable revision IDs plus complete input snapshots. Exact active evidence transaction IDs override fallible categories so savings and debt outflows cannot be counted twice; reversing savings evidence restores the ordinary debit. Every report-affecting write takes the household lock before changing canonical state; the report cutoff is chosen only after that lock is held. Normal payday closure is distinct from a late/invalidated-boundary correction. Interactive refreshes are bounded to 1,000 verified receipts, 80 recent boundaries, and 24 warm reports; list reads are read-only and one older detail is refreshed on demand. Stale, pre-transaction, missing, role-changing, or account-type-changing balance coverage lowers assurance rather than fabricating reconciliation. Fully provider-backed evidence is `complete`; structurally complete manual evidence is `user_confirmed`. List and planning history are independently paginated with lossless seek cursors, and native devices retain an encrypted, identity-scoped read-only copy. Export format 4 and deletion include every planning, boundary, cycle, report, input and coverage record.
- Savings goals are explicit, optional records with one protected destination per active goal. Connected destinations are limited to savings accounts; checking and cash accounts cannot be reclassified as a goal. Their planned contribution affects safe-to-spend, while progress is derived only from immutable movements. An existing account balance counts only after the user explicitly allocates it to the goal.
- Automatic connected-account tracking begins at the exact instant the destination is attached when bank history is complete. If an account is visible while its first historical import is still running, tracking remains inactive until that import commits, then starts after the imported transactions. Provider evidence recorded before the boundary stays historical, while transactions synchronized later the same day remain eligible. The bounded withdrawal scan considers at most the prior 180 days.
- A connected contribution is automatically provider-verified only when Budgefi has one unambiguous source debit, the exact destination credit, and later balance observations for both accounts. A proposal can upgrade after a later synchronization supplies balance evidence. Destination-only or ambiguous evidence is reviewable; source-only evidence proves nothing. Manual progress is labeled “confirmed by you.” Protected withdrawals reduce progress, provider reversals append compensating movements, and protected-to-protected reallocations do not masquerade as withdrawals.
- Cash cushion is a separate optional guardrail. It leaves spendable cash untouched and never claims that money was moved to savings.
- Debt visibility treats each card or loan as a liability account with at most one linked payment commitment. Provider `current` liability balance—not available credit—is preserved as signed evidence, while displayed owed is floored at zero and never enters spendable cash. When an institution supports Plaid Liabilities, Budgefi stores minimum/due/statement facts and each APR component as separate provider observations; absent fields stay unknown and manual review never blocks onboarding. A payoff estimate uses the amount of the active linked commitment—not unreserved policy inputs—and appears only when fresh balance and a selected APR exist, with an explicit no-new-charges assumption. Budgefi-managed commitments are updated atomically with debt name, due date, payment, and extra amount, and retired on unlink/archive/disconnect. Connected payments may be partial and remain proposals until an unambiguous spendable-account debit, matching liability-account credit, and later balances for both sides agree. Evidence reversals are append-only and release revised transaction evidence for a replacement match. Budgefi does not derive principal reduction from a payment, choose snowball/avalanche ordering, or recommend a payoff strategy.
- CSV import and accounting-grade reporting. Transaction browsing/search and optional categorization are implemented, but categories are organizational labels rather than financial advice.
- Android FCM delivery. iOS APNs/email require provider configuration and device validation.
- Money movement, investment trading, debt optimization or financial advice.

## Change checklist

Before changing a flow, verify: identity and household scope; idempotency; expected version; household revision; integer-money validation; provenance; append-only evidence; offline behavior; retry/lease behavior for external calls; deletion/export inclusion; honest copy; and both manual and connected paths. Schema changes require a forward-only migration and a fresh-database integration test. External provider work must be durable before the HTTP response reports acceptance.
